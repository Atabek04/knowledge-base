## Git Basics

- What is **Git**
    
    Free and open source version control system
    
- What is **Version Control** ?
    
    The management of changes in docs, apps, large web sites ad so on.
    
- How to **set your details ?**
    
    ```bash
    git config --global user.name "Your Name"
    git config --global user.email "your.email@example.com"
    ```
    
- **Why** you need to **set your details** ?
    - Setting your user name and email in Git is crucial because it associates your identity with your commits.
        - This way, every change you make in the repository is tagged with your name and email, making it clear who made each change.
- How to **Initialize a Git** Repository **?**
    
    ```bash
    git init
    ```
    
    - This creates a hidden `.git` folder in your project directory, which Git uses to store your project’s history.
- How to **stage** your changes **?**
    
    To track a specific file:
    
    ```bash
    git add filename
    ```
    
    To track all changes in the dir:
    
    ```bash
    git add .
    ```
    
- How to **unstage** the changes **?**
    
    Unstage a specific file:
    
    ```bash
    git reset HEAD fileName
    ```
    
    Unstage all changes:
    
    ```
    git reset HEAD
    ```
    
- How to **commit** your changes **?**
    
    ```bash
    git commit -m "Your commit message here"
    ```
    
    - he `-m` flag allows you to add a commit message directly from the command line.
- How to **combine staging and committing** ?
    
    ```bash
    git commit -am "Your commit message here"
    ```
    
    <aside>
    ⚠️ **Note**
    
    The `-a` flag only stages changes to files that are already being tracked by Git. 
    
    It won't stage new files that haven't been added yet, only modified.
    
    </aside>
    
- How to **undo the commit** ?
    1. **Undoing commit, but keeping changes & staged in working dir**
        
        ```bash
        git reset --soft HEAD~1
        ```
        
    2. **Undoing commit and keeping changes but unstaged the changes**
        
        ```bash
        git reset (--mixed) HEAD~1
        ```
        
    3. **Undoing commit and discarding the changes**
        
        ```bash
        git reset --hard HEAD~1
        ```
        
    4. **Undoing specific commit**
        
        First **find the commit-hash** with:
        
        ```bash
        git log
        ```
        
        and then revert the changes:
        
        ```bash
        git revert <commit-hash>
        ```
        
- What’s the **diff between `git reset` and `git revert`** ?
    
    **When to use `git reset` :**
    
    - When you want to **completely** **remove one or more commits from your branch’s history**.
    - **Best used on local branches** that haven’t been pushed to a remote repository yet.
    
    > ⚠️ **Caution:** *Using git reset on a shared branch that others are working on can lead to conflicts and confusion, as it **rewrites history**.*
    > 
    
    ---
    
    **When to use `git revert` :**
    
    - When you need to **undo changes BUT keep the commit history**, especially in a shared or public branch.
    - **Ideal** for undoing **changes that have already been pushed** to a remote repository.
- How to **apply the changes at specific commit** ?
    - First find the commit you want to apply using `git log` or another method to get the commit hash, and then use this command:
        
        ```bash
        git cherry-pick <commit-hash>
        ```
        
        - If there are conflicts, Git will pause the cherry-pick process and mark the files with conflicts.
        - After resolving the conflicts, stage the resolved files using `git add <file>`
        - Once all conflicts are resolved and staged, continue the cherry-pick process with:
            
            ```bash
            git cherry-pick --continue
            ```
            
        - If you decide you don't want to continue with the cherry-pick, you can abort it with:
            
            ```bash
            git cherry-pick --abort
            ```
            
- How to **find the hashes** of recently **removed commits** ?
    
    ```bash
    git reflog
    ```
    
- How to **fetch repo changes** ?
    
    ```bash
    git fetch
    ```
    
    - Use `git fetch` when you want to **see what changes are available in the remote repository WITHOUT affecting your current work**.
        - It's a safe way to check for updates.
- How to **view fetched commits & changes** ?
    
    ```bash
    git log HEAD..origin/main --oneline
    ```
    
    - **HEAD**: A pointer to the latest commit in your current branch.
        - It represents "where you are now" in the commit history.
    - This command shows all commits that exist in **`origin/main`** but are not in your current branch (HEAD).
        - It answers "what commits will I get if I merge/pull from origin/main?"
    
    ---
    
    Alternatively, you can use git diff to see the actual code differences:
    
    ```bash
    git diff HEAD..origin/main
    ```
    
    This will display the differences between your current branch and the origin/main branch.
    
- What **actions** can be done **after fetching** ?
    
    After fetching the changes, you typically want to **incorporate them into your local branch**. There are a couple of ways to do this:
    
    1. **Merging**: You can merge the fetched changes into your current branch using `git merge`.
    2. **Rebasing:** Alternatively, you can rebase your current branch on top of the fetched changes using `git rebase`.
    
    ---
    
    For example, if you fetched changes from the `origin/main` branch, you could merge them into your current branch with:
    
    ```bash
    git merge origin/main
    ```
    

## Branches

- How to **merge** ?
    1. **Switch to the Target Branch**
        
        First, you need to **be on the branch you want to merge changes into**. This is typically the main or develop branch:
        
        ```bash
        git checkout main
        ```
        
    2. **Merge the Source Branch**
        
        Next, merge the branch that has the changes you want to bring in. For example, if you’ve completed work on a feature branch and want to merge it into main:
        
        ```bash
        git merge feature-branch
        ```
        
        > 🗒️ *If there would be conflict, **solve** them then **stage** the resolved files, then complete the merge by **committing** the changes.*
        > 
    3. **Push the Merge to the Remote Repository:**
        
        After a successful merge, you typically push the merged changes back to the remote repository:
        
        ```bash
        git push origin main
        ```

- What is **rebasing** ?
    - **Rebasing** is a Git operation that lets you **move or “replay” your commits** **on top of another branch**
        
        ```bash
        A---B---C   (main)
             \
              D---E (feature-branch)
        ```
        
    - If you rebase feature-branch onto main, Git will replay the commits from feature-branch (D and E) on top of the latest commit on main (C):
        
        ```bash
        A---B---C---D---E (feature-branch rebased onto main)
        ```
        
    - The commits `D` and `E` are the **same as previous**, but are now **new commits (new hashes)** that appear as if they were made after C.
- How to **rebase** ?
    1. **Start a Rebase**
        
        ```bash
        git checkout feature-branch
        git rebase main
        ```
        
    2. **Handling Conflicts**
        
        ```bash
        git rebase --continue
        ```
        
    3. **Abort a Rebase** (if needed)
        
        ```bash
        git rebase --abort
        ```
        
- **When** to use **rebasing** ?
    - **To keep a clean, linear history:** Rebasing avoids the merge commits, creating a more straightforward history.
    - **Before merging a feature branch:** Rebasing onto the main branch before merging can integrate the latest changes without adding unnecessary merge commits.
        - **Without Rebasing First**
            
            ```bash
            A---B---C---D---E (`main`)
                 \
                  F---G---H (`feature`)
            
            # After merge:
            A---B---C---D---E-------M (`main`)
                 \             /
                  F---G---H---/ (`feature`)
            ```
            
        - **With Rebasing First**
            
            ```bash
            A---B---C---D---E (`main`)
                 \
                  F---G---H (`feature`)
            
            # After rebase:
            A---B---C---D---E (`main`)
                             \
                              F---G---H (`feature`)
            
            # After merge:
            A---B---C---D---E---F---G---H (`main, feature`)
            ```
            
- When to use `git merge` and `git rebase`
    
    ### **When to Use `git merge`:**
    
    - **Preserving History**: If you want to keep the history of both branches intact, including the context of when and why changes were made, merging is a good choice. This is especially useful in collaborative projects where understanding the sequence of changes is important.
    - **Complex Histories**: When dealing with complex histories or multiple contributors, merging can make it easier to see how different branches have evolved and interacted over time.
    
    ### **When to Use `git rebase`:**
    
    - **Clean History**: If you prefer a clean, linear history without the clutter of merge commits, rebasing is the way to go. This can make the commit history easier to read and follow.
    - **Feature Branches**: When working on a feature branch, you might rebase onto the main branch before merging to ensure that your feature branch is up-to-date with the latest changes and to avoid merge conflicts.
    
    ---
    
    **Here's a simple analogy:**
    
    - **Merging** is like combining two roads into one, where you can see the paths both roads took to get there.
    - **Rebasing** is like picking up one road and placing it on top of another, creating a single, straight path.
- What’s a **stashing** ?
    - **Stashing** is a way to temporarily save changes in your working directory that are not yet ready to be committed.
        - This allows you to switch branches or perform other tasks without losing your uncommitted changes.

- **When** to use **stashing** ?
    - **When you need to switch branches:** If you need to change branches but have uncommitted work, stashing allows you to save your changes temporarily.
    - **To keep your working directory clean:** If you’re not ready to commit but want to work on something else, stashing helps keep things tidy.
- How to **push the changes** ?
    
    ```bash
    git push origin branch-name
    ```
    
    - **origin**: This is the default name for the remote repository, though it can be different if you’ve set it up that way.
    - **branch-name**: This is the branch you want to push, such as main, develop, or feature/xyz.
- What is **force push** ?
    - A **force push** is a more aggressive version of the push command.
        - It allows you to overwrite changes on the remote branch, which can be risky if not used carefully.
        
        ```bash
        git push --force origin feature-branch
        ```
        
- **When** to use **force push** ?
    - **After a Rebase:** When you rebase your commits on top of another branch, your commit history is rewritten.
        - To update the remote branch with this new history, you may need to force push.
            
            ```bash
            git push --force origin feature-branch
            ```
            
    - **To Overwrite Remote Changes:** If you need to overwrite the commits on the remote branch (e.g., to undo someone else’s changes), a force push can be used.
        - However, this is generally discouraged in shared branches like main because it can lead to lost commits for other collaborators.
- **Risks** of **Force Pushing** ?
    - **Overwriting Others’ Work**: If someone else has pushed changes to the remote branch that you haven’t pulled or incorporated into your local branch, a force push can overwrite those changes, potentially causing data loss.
    - **Disrupting the History**: Force pushing alters the commit history, which can confuse collaborators and make it harder to trace changes.
- What’s a **safer alternative of force push** ?
    
    ```bash
    git push --force-with-lease origin feature-branch
    ```
    
    - It behaves like a `force push` but with a safeguard:
        - it only forces the push if the **remote branch hasn’t been updated since you last fetched it**.
        - If someone else has pushed to the remote branch, the push will be rejected, preventing accidental overwrites.

## Tags

- What’s **Tag** ?
    - **Tag** is a **named reference to a commit**
    - Tags allow marking points in history as important
        - Frequently used to mark **software release versions** (v1.0, v1.1, v2.0)
        - Can mark **key features** or changes (ecommerce, redesign)
        - Can mark points for discussion with collaborators (bug, issue_136)
- How to **create tags** ?
    - There are two types of tags in Git:
        - **lightweight tags**
        - **annotated tags**
    
    ---
    
    - A **lightweight tag** is essentially a pointer to a specific commit.
        - It doesn't store any additional metadata beyond the commit it points to.
            
            ```bash
            git tag <tagname> <SHA_COMMIT>
            # example:
            git tag v1.0 dd5c4928o
            ```
            
            - If you leave SHA as a blank that it will point to the current commit.
    
    ---
    
    - An **annotated tag** is a **full object** in the Git database. It stores additional metadata, including the tagger's name, email, date, and a message.
        - Annotated tags are recommended for marking releases because they provide more information.
            
            ```bash
            git tag -a <tagname> -m "Tag message" <SHA_COMMIT>
            # example:
            git tag -a v1.0 -m "Release version 1.0" dd5c4928o
            ```
            
- How to **delete tag** ?
    
    ```bash
    git tag -d v1.0  #same as: git tag --delete v1.0
    ```
    
    > ℹ️ It deletes tag, but the commit that this tag was referencing is still there.
    > 
- How to **delete remote tags** ?
    
    ```bash
    git push -d origin v1.0
    ```
    
    <aside>
    
    Git doesn't automatically know that **`v1.0`** is a tag in this command. The command works this way:
    
    1. Git first checks if **`v1.0`** is a branch name
    2. If not found as a branch, it checks if **`v1.0`** is a tag name
    3. It then deletes the matching reference on the remote
    </aside>
    
- How to **list the tags** ?
    
    List tags alphabetically:
    
    ```bash
    git tag
    git tag -l # --list
    ```
    
    ---
    
    List tags beginning with “v2”
    
    ```bash
    git tag -l "v2*"
    ```
    
    ---
    
    List tags with first line of each annotation
    
    (`-n` implies `-l`)
    
    ```bash
    git tag -n
    ```
    
    List tags with five line of each annotation
    
    ```bash
    git tag -n5
    ```
    
    ---
    
    Work with tags
    
    ```bash
    git show v1.1
    ```
    
    ```bash
    git diff v1.0..v1.1
    ```
    
    ```bash
    git swtich -c branch_v1 v1.0
    ```
    
- How to **push the tags** ?
    
    Push a single specific tag:
    
    ```bash
    git push origin v1.0
    ```
    
    Push all tags to a remote repo:
    
    ```bash
    git push origin --tags
    ```
    
- How to **fetch the tags** ?
    
    Fetch commits and tags:
    
    ```bash
    git fetch
    ```
    
    Fetch only tags (with necessary commits):
    
    ```bash
    git fetch --tags
    ```
    

## Interactive Staging

- What’s an **interactive staging** ?
    - Interactive staging - stages changes interactively
    - Allows **staging portions of changes** files
    - Helps to make **smaller, focused commits**
    - Feature of many **Git GUI tools**
- How to **enter to interactive staging mode** ?
    
    ```bash
    git add -i # --interactive
    ```
    
- What’s a **patch mode** ?
    
    **Patch mode** - allows staging portions of a changes file
    
- Difference between **Interactive mode** and **Patch mode ?**
    - Interactive mode is a broader concept with multiple operations
    - Patch mode is specifically about selecting portions of changes
    - In some commands like **`git add -i`**, patch mode is available as one of the options within interactive mode
- What’s a **hunk** ?
    - Hunk an area where two files differ (small part of code)
    - Hunks can be staged, skipped, or split into smaller hunks
- How to **enter to patch mode**  ?
    
    First you enter interactive staging mode, then from it choose patch mode:
    
    ![Screenshot 2024-08-17 at 19.07.28.png](Screenshot_2024-08-17_at_19.07.28.png)
    
    You can enter directly:
    
    ```bash
    git add --patch
    git add -p
    
    git stash -p
    git reset -p
    git restore -p
    git commit -p
    ```
    
- What is criteria to **split the hunk** ?
    
    It **requires** **one or more unchanged lines** between changes
    
- How to **split the hunk** ?
    
    Enter to patch mode, then enter `s`
    
- **Why** we need to **edit a hunk** ?
    
    When a hunk cannot be split automatically
    
- How to **enter to edit mode** ?
    
    First enter to patch mode, then enter `e`
    
- What’s **cherry-picking** commits ?
    - Applying the changes from one or more existing commits
    - Each commit targeted will become a new commit on the current branch
        
        ```bash
        git cherry-pick d48411d09
        git cherry-pick d4e8411d09..57290ec44
        ```
        
        - 2nd command picks a range of commits, from the commit *after* d4e8411d09 up to and including 57290ec44
        - First commit in the range isn't included, only its descendants.
        - If you want to include the first commit too, you'd use:
            
             **`git cherry-pick d4e8411d09^..57290ec44`**
            
        
        ---
        
    - New commits have different SHAs
    - You can cherry-pick from any branches
        - But you can’t cherry-pick a merge commit
    - You can use `--edit` or `-e` to edit the commit message
    - Also it can result in conflicts that must be resolved
        - After you resolving you can run `git cherry-pick --continue`
        - If you wanna skip this commit, you can run `git cherry-pick --skip`
        - Or you abort all changes by `git cherry-pick --abort`
- What’s a **SHA** ?
    - SHA stands for **Secure Hash Algorithm**. It's used to **uniquely identify commits**
    - Every time you make a commit in Git, it **generates a SHA-1 hash**, which is a **40 character** string
    - Git allows you to use a shortened version of the SHA-1 hash. Typically, the first 7 characters are enough to uniquely identify a commit in most repositories.
        - For example, if your full SHA-1 hash is `e1a1e3b5c6d7f8a9b0c1d2e3f4a5b6c7d8e9f0a1`, you can usually just use `e1a1e3b` to refer to that commit.
- What’s a **Diff Patches** ?
    - Diff pathces allows us share changes via files
    - It’s useful whne changes aren’t ready for a public branch
    - Or when collaborators don’t share remote
    - Pathces used on discussion, review, approval process
- How to **create a diff patch** ?
    
    ```bash
    git doff from-commit to-commit > output.diff
    ```
    
- How to **apply the diff patch** ?
    
    ```bash
    git apply output.diff
    ```
    
- How to **restore files** ?
    1. **Restoring Files in the Working Directory**
        
        This is useful if you want to discard changes in your working directory and revert to the last committed state of a file. For example:
        
        ```bash
        git restore <filename>
        ```
        
    2. **Restoring Files from a Specific Commit**
        
        ```bash
        git restore --source=<commit-SHA> <filename>
        ```
        
- What’s a **formatted patch** ?
    - Export each commit in Unix mailbox format
    - Useful for email distrubution of changes
    - Includes commit changes
    - One commit per file by default
- How to **create a formatted patch** ?
    
    Export all commits in the range:
    
    ```bash
    git format-patch 2e33d..655da
    ```
    
    Export all commits on current branch that are not in main branch
    
    ```bash
    git format-patch main
    git format-patch main..HEAD
    ```
    
    Export a single commit
    
    ```bash
    git format-patch -1 665da
    ```
    
    Put patch files into a directory
    
    ```bash
    git format-patch 2e33d..655da -o ~/feature_patches
    ```
    
    Output patches as a single file
    
    ```bash
    git format-patch 2e33d..655da --stdout > feature.patch
    ```
    
    - 
- What will happen after applying formatted pathces ?
    - Extract author, commit message, and changes from a mailbox message and apply them to the currrent branch
    - Similar to cherry-picking: same changes, different SHAs
    - Commit history is transferred
- How to **apply formatted patches** ?
    
    Apply single patch
    
    ```bash
    git am feature/001-some-name.patch
    ```
    
    Apply all patches in a directory
    
    ```bash
    git am feature/*.patch
    ```
    

## Rebasing

- What’s an **interactive rebasing** ?
    - Chance to modify commits as they are begin replayed
    - Opens the git-rebase-todo file for editing
    - Can reorder or skip commits
    - Can edit commits contents
    
    ---
    
    Interactive Rebase Choices:
    
    - pick, drop
    - reword, edit
    - squash, fixup
    - exec
- How to **interactive rebase** ?
    
    ```bash
    git rebase -i main new_feature
    ```
    
- What’s a **squash commits** ?
    - Fold two or more commits into one
    - **squash:** combine change sets, concatenate messages
    - **fixup**: combine change sets, discard this message
    - Uses first author in the commit series
- What’s the `--set-upstream` in the `git push` ?
    - When you use `--set-upstream`, Git sets the specified remote branch as the upstream branch for your current local branch. This means that Git will remember which remote branch your local branch is tracking, making it easier to push and pull changes in the future.
        - Once the upstream branch is set, you can simply use `git push` or `git pull` without specifying the remote and branch each time.
            
            ```bash
            git push --set-upstream <remote> <branch>
            ```
            
- What’s a `pull rebase` ?
    - Fetch from remote, then rebase instead of merging
    - Kepps history cleaner by reducnig merge commits
    - Only use on local commits not shared to a remote
- How to `pull rebase` ?
    
    ```bash
    git pull -r
    git pull --rebase
    ```
    
    ```bash
    git pull --rebase=preserve
    	git pull --rebase=interactive
    ```
    

## Track Down Problems

- What’s a Log ?
    - Log is the primary interface to Git
    - Log has many optoins
    - Sorting, Filtering, output formating
    - git help log
- How to create log ?
    
    List commits that changed filename.txt
    
    ```bash
    git log filename.txt
    ```
    
    List commits as patches (diffs)
    
    ```bash
    git log -p
    git log --patch
    ```
    
    List changes to lines 100-150 in filename.txt
    
    ```bash
    git log -L 100,150:filename.txt
    git Log -L 100,+50:filename.txt 
    ```
    
- What’s a **Blame** ?
    - Blame allows us browse annotated file
    - **Determine who changed which lines in a file and why**
    - Useful for probing the history behind a file’s contents
    - Useful for identifying which commit introduced a bug
- How to create blame ?
    
    Annotate fil with commit details
    
    ```bash
    git blame filename.txt
    ```
    
    Ignore whitespace
    
    ```bash
    git blame -w filename.txt
    ```
    
    Annotate lines 100-150
    
    ```bash
    git blame -L 100,150 filename.txt
    ```

- What’s a **VCS** ?
    
    **VCS (Version Control System)** is a tool or system used to manage and track changes to files, codebases, documents, and other forms of content over time. 
    
    It allows multiple people to collaborate on projects, keeps a history of every modification, and helps in merging changes from different team members. 
    
    VCS also enables users to revert to previous versions of files, which is crucial for fixing errors and understanding the history of a project.
    
- What are the **types of VCS** ?
    
    Version Control Systems are generally categorized into three types:
    
    1.	**Local Version Control Systems**
    
    2.	**Centralized Version Control Systems (CVCS)**
    
    3.	**Distributed Version Control Systems (DVCS)**
    
- What’s a **Local VCS ?**
    
    **Local VCS** involves keeping track of files’ versions on your local machine. This was a basic method where developers maintained copies of files in different directories to track changes manually.
    
    ---
    
    **Example**: **RCS (Revision Control System)**
    
    - **How It Works**: RCS keeps track of changes by storing patch sets (differences between file versions) in a special format on the local disk. This allows users to revert files to earlier versions by applying the reverse patches.
    
    **Limitations**:
    
    - It only works on a single machine, which makes it difficult to collaborate with others.
    - No networked sharing of code, limiting the ability to work as a team.
- What’s a **CVCS ?**
    
    **Centralized VCS** uses a single central server to store all versions of the project files. The central repository contains all the versioned files, and team members check out files and work on them locally. They can commit their changes back to the central server.
    
    ---
    
    **Examples**: **Subversion (SVN)**, **Perforce**, **CVS (Concurrent Versions System)**
    
    - **How They Work**: Users check out files from a central repository to their local machine, make changes, and then commit those changes back to the central repository. This system allows team members to see each other’s work, but it requires network access to the central server to perform operations.
    
    **Advantages**:
    
    - Centralized control: Easy to administer, with a single repository to manage.
    - Simple model: Easy to understand and use, with one central location for all files.
    
    **Disadvantages**:
    
    - Single point of failure: If the central server goes down, no one can commit changes.
    - Limited offline capabilities: Users cannot commit changes without being connected to the server.
- What’s a **DVCS ?**
    
    **Distributed VCS** is a more modern approach where every user has a full copy of the repository on their local machine, including the entire history of changes. Users can work independently and commit changes locally, without the need for a network connection. When ready, they can push or pull changes to and from other repositories.
    
    ---
    
    **Examples**: **Git**, **Mercurial**, **Bazaar**
    
    - **How They Work**: In DVCS, every user has a local copy of the entire project history. Users can commit changes locally and synchronize with others by pushing or pulling changes from remote repositories.
    
    **Advantages**:
    
    - No single point of failure: Since every user has a full copy of the repository, if one repository is lost, any other copy can be used to restore it.
    - Offline capabilities: Developers can commit and review history without a network connection.
    - Better branching and merging: DVCS generally handles branching and merging more efficiently than CVCS.
    
    **Disadvantages**:
    
    - Complex to manage for beginners: Understanding the full capabilities and best practices of DVCS can be more challenging for newcomers.

- Explain the basic concepts of Git, such as the working tree, indices, and branches
    1. **Working Tree (Working Directory)**
        
        The **working tree** (or working directory) is the directory on your local machine where you are currently working on your project files. It reflects the most recent state of the files, including any changes you’ve made that haven’t been committed yet.
        
        - **Untracked Changes**: Files that exist in the working directory but haven’t been added to Git are considered untracked.
        - **Modified Files**: If you edit a file that is already tracked by Git, it will be shown as modified in the working tree.
        
        The working tree allows you to see and modify the actual contents of your project before deciding which changes to stage or commit.
        
    
    ---
    
    1. **Index (Staging Area)**
        
        The **index**, also known as the **staging area**, is an intermediate area where changes are gathered before they are committed to the repository.
        
        - **Staging Changes**: When you make changes in your working directory and want to include them in the next commit, you need to add them to the staging area using 
        `git add`
        - **Commit Preparation**: The index serves as a preview of what your next commit will look like. You can stage changes selectively, meaning you can add specific files or even specific parts of files to the staging area.
        
        The index is crucial because it lets you build your commits incrementally, allowing more control over what changes are recorded in the history.
        
    
    ---
    
    1. **Branches**
        
        A **branch** in Git is a pointer to a specific commit in the repository. It represents a line of development and allows you to diverge from the main line of development to work on features, bug fixes, or experiments in isolation.
        
        - **Main Branch**: The main (or master in older projects) branch is usually the default branch that contains the stable version of the code.
        - **Feature Branches**: You can create a new branch (git branch feature-xyz) to work on a specific feature without affecting the main codebase. Once the feature is complete, you can merge the branch back into main.
        - **Branching and Merging**: Branches allow for parallel development. After finishing work on a branch, you can merge it into another branch (e.g., main) using 
        `git merge`
        
        Branches in Git are lightweight and cheap to create, making them a powerful tool for managing different lines of development in a project.
        
- What is HEAD in Git? How can it be detached and reattached?
    
    **HEAD** in Git is a reference to the current branch or commit you are working on. It points to the latest commit in your current branch. Think of HEAD as a pointer that tells Git which snapshot of the project you are currently viewing or making changes to.
    
    - **Current Branch Reference**: Normally, HEAD points to the latest commit in your active branch (like main or develop). When you make new commits, Git updates the branch’s pointer to the new commit and moves HEAD forward to the latest commit.
    - **Symbolic Reference**: HEAD is often a symbolic reference that points to the branch name, which in turn points to the actual commit. For example, if you’re on the main branch, HEAD might point to refs/heads/main.
    
    ---
    
    **Detached HEAD**
    
    A **detached HEAD** state occurs when HEAD points directly to a commit rather than to a branch. This typically happens when you check out a specific commit instead of a branch. In this state, you’re “detached” from any branch, and any new commits you make will not belong to any branch. These commits can easily become “orphaned” if you switch to another branch without doing anything with them.
    
    **How It Happens:**
    
    - **Checking Out a Commit**: Running a command like `git checkout <commit-hash>` causes HEAD to point directly to that commit, detaching it from any branch.
    - **Checking Out a Tag**: Similarly, checking out a tag (e.g., `git checkout v1.0.0`) also detaches HEAD, since tags are also pointers to specific commits, not branches.
    
    **Risks of Detached HEAD:**
    
    Any new commits made in this state won’t be associated with any branch. If you switch to a branch afterward, those commits will be lost unless you create a new branch or explicitly move them to another branch.
    
    ---
    
    **Reattaching HEAD**
    
    **Saving Work Done in a Detached HEAD State**
    
    If you’ve made commits while in a detached HEAD state and want to keep them:
    
    1. **Create a New Branch:**
        - You can create a new branch that includes the commits you’ve made.
        
        ```bash
        git checkout -b new-branch-name
        ```
        
        This command creates a new branch from your current commit and attaches HEAD to this new branch.
        
    2. **Cherry-Pick Commits**:
        
        Alternatively, you can switch back to an existing branch and use git cherry-pick to apply the commits from the detached HEAD state to that branch.
        
- Can you explain the difference between '@~' and '@^' in Git usage?
    
    In Git, @~ and @^ are both shorthand notations used to reference specific commits relative to a particular commit (usually HEAD), but they operate slightly differently. Understanding these notations is essential for navigating and working with Git history.
    
    ---
    
    **@~ (Tilde Operator)**
    
    The tilde (~) operator is used to refer to the **n-th ancestor** of a commit. By default, @~ refers to the immediate parent of the commit. If you want to go back more than one generation, you can add a number after the tilde.
    
    - **@~**: This refers to the parent commit of the current commit 
    (e.g., HEAD~ refers to the parent of HEAD).
    - **@~2**: This refers to the grandparent of the current commit 
    (e.g., HEAD~2 refers to the parent of the parent of HEAD).
    
    ```bash
    git log HEAD~1
    ```
    
    This command shows the commit history starting from the parent of the current commit.
    
    ---
    
    **@^ (Caret Operator)**
    
    The caret (^) operator is used to refer to the **first parent** of a commit, but it also has additional functionality in the context of merge commits.
    
    - **@^**: Like @~, this refers to the first parent of the current commit. However, if the current commit is a merge commit (which has more than one parent), @^ refers to the first parent.
    - **@^2**: This specifically refers to the second parent of a merge commit. For example, in a merge commit, @^1 refers to the first parent (usually the branch you were on), and @^2 refers to the branch that was merged in.
    
    ```bash
    git log HEAD^
    ```
    
    This command shows the commit history starting from the first parent of the current commit.
    
    ---
    
    **Differences and Use Cases**
    
    - **Navigating Ancestry**:
        - Use @~n to move back n generations in the commit history.
        - Use @^n to refer to specific parents of a merge commit, especially useful when you need to reference which branch was merged into another.
    - **Merge Commits**:
        - For a non-merge commit, @~ and @^ are functionally equivalent, as both refer to the first parent.
        - For a merge commit, @~ still refers to the first parent (like @^), but only @^n allows you to reference other parents (e.g., @^2 for the second parent).

      **Scenario Setup**  
    
    ```bash
    A --- B --- C ------- E (HEAD)
           \            /
            D ------- F
    ```
    
    - **HEAD**: Points to commit E.
    - **`HEAD~`  ⇒  C**
    - **`HEAD~2`  ⇒  B**
    - **`HEAD^`  ⇒  C**
    - `HEAD^2`  **⇒**  **F**

- What are rebasing, merging, and cherry-picking in Git, and what distinguishes them from each other?
    1. **Merging**
        
        **Merging** is the process of combining changes from one branch into another. When you merge, Git creates a new commit (a merge commit) that brings together the histories of both branches.
        
        **Scenario**: You have a feature branch and want to integrate it into the main branch after completing the feature.
        
        ```bash
        git checkout main
        git merge feature
        ```
        
        **When to Use**:
        
        - When you want to preserve the history of both branches.
        - When you’re integrating completed features, bug fixes, or updates back into the main branch.
        - When working in a team and you want to retain the context of all contributors’ work.
        
        ---
        
    2. **Rebasing**
        
        **Rebasing** is the process of moving or combining a series of commits to a new base commit. It rewrites the commit history by applying your changes on top of another branch’s history.
        
        **Scenario**: You’re working on a feature-branch and want to incorporate the latest changes from the main branch before completing your work.
        
        ```bash
        git checkout feature
        git rebase main
        ```
        
        **When to Use**:
        
        - When you want to keep a clean, linear project history.
        - Before merging a feature branch into main, rebasing it onto main helps to integrate the latest changes from main without creating a merge commit.
        - For small, individual branches where you don’t need to preserve the branch’s original context.
        
        ---
        
    3. **Cherry-Picking**
        
        **Cherry-picking** is the process of applying a specific commit from one branch into another branch. It allows you to pick individual changes from another branch without merging the entire branch.
        
        **Scenario**: You need to apply a critical bug fix from hotfix-branch to main without merging other unrelated commits.
        
        ```bash
        git checkout main
        git cherry-pick <commit-hash>
        ```
        
        **When to Use**:
        
        - When you need to apply a specific commit or set of commits from one branch to another.
        - When you want to bring in a specific change without merging the entire branch.
        - Useful in release management, where only certain changes need to be backported to an earlier version.
- What is git GC, what is its purpose, and how can one interact with it?
    - `git gc` stands for “Git Garbage Collection.”
        - It’s a Git command used to clean up unnecessary files and optimize the local repository.
        - Over time, as you make changes, commits, branches, and merges, your Git repository accumulates various files that can take up space and slow down operations. `git gc` helps manage this by performing a variety of housekeeping tasks.
        
        ---
        
    - The primary purpose of `git gc` is to:
        - **Clean Up Unnecessary Files**:
            - Git operations often generate temporary files, logs, or other objects that may no longer be needed. git gc identifies and removes these, helping to reduce the size of the repository
        - **Pack Loose Objects**:
            - Git stores objects (like commits, trees, and blobs) in a .git/objects directory. Over time, many of these objects might be stored as “loose objects,” which are individual files taking up space. git gc compacts these loose objects into pack files, which are more space-efficient and faster to access.
        - **Prune Unreachable Objects**:
            - When you delete branches, reset, or rewrite history, some commits and objects might become “unreachable” (no branch or tag points to them). git gc can remove these unreachable objects if they are older than a certain age.
        - **Optimize the Repository:**
            - By cleaning up unnecessary files and packing objects, git gc can significantly improve the performance of your Git operations, especially in large repositories
        
        ---
        
        **How to Use git gc**
        
        1. **Run git gc Manually**:
            
            ```bash
            git gc
            ```
            
        2. **Auto Garbage Collection:**
            
            Git also runs garbage collection automatically when certain thresholds are exceeded (e.g., too many loose objects). This is usually done in the background during regular Git operations.
            
        3. **Options for git gc**:
            - **`--prune=<date>`**: Prunes objects older than the specified date.
                
                ```bash
                git gc --prune=now
                ```
                
                *This command prunes all unreachable objects immediately, regardless of their age.
                
            - **`--aggressive`**: Performs a more thorough garbage collection, which might take longer but can result in greater optimization.
                
                ```bash
                git gc --aggressive
                ```
                
            - **`--auto`**: This option runs garbage collection only if Git determines that it is necessary. This is the default behavior that happens during normal operations.
                
                ```bash
                git gc --auto
                ```

- What occurs inside the .git/ directory?
    - The .git/ directory is the heart of any Git repository.
        - It contains all the metadata and object database for the version history of your project.
        - When you initialize a Git repository using `git init`, this directory is created and populated with various files and subdirectories that Git uses to *track changes*, *manage branches*, *store* *commit history*, and more.
        
        ---
        
    
    **Key Components of the .git/ Directory**
    
    - **HEAD**
        - **What it is**: A file that points to the current branch or commit that your working directory is based on.
        - **Purpose**: It tells Git which branch you are currently on. If you’re in a “detached HEAD” state, it will point to a specific commit rather than a branch.
    - **config**
        - **What it is**: A file that stores configuration settings for the repository.
        - **Purpose**: It contains repository-specific settings like remotes, branches, and user information. These settings override global Git configurations.
    - **description**
        - **What it is**: A file containing a description of the repository.
        - **Purpose**: Primarily used by Git web interfaces. It’s not usually important for command-line Git operations.
    - **hooks/**:
        - **What it is**: A directory containing sample scripts that can be triggered by certain Git actions (e.g., committing, merging).
        - **Purpose**: These scripts allow you to automate tasks, enforce policies, or trigger actions during events like pre-commit, pre-push, etc.
    - **info/**:
        - **What it is**: Contains the `exclude` file and other miscellaneous information
        - **Purpose**: The `exclude` file within this directory functions similarly to .gitignore but is not shared with others. It’s for excluding files from version control locally.
    - **objects/**:
        - **What it is**: The directory where Git stores all content (blobs, trees, commits) as compressed objects.
        - **Purpose**: This is the object database where every piece of data Git tracks is stored as an object. These objects include:
            - **Blobs**: Represent the contents of files.
            - **Trees**: Represent directories and their contents.
            - **Commits**: Store metadata and pointers to tree objects.
    - **refs/**:
        - **What it is**: A directory that contains references to commit objects.
        - **Purpose**: Stores pointers to specific commits. This includes:
            - **heads/**: Points to the latest commit on branches.
            - **tags/**: Points to specific commits marked by tags.
            - **remotes/**: Tracks branches in remote repositories.
    - **index**:
        - **What it is**: A binary file that serves as the staging area.
        - **Purpose**: The index holds a snapshot of the working directory that is staged for the next commit. It’s essentially where changes are prepared before they are committed.
    - **logs/**:
        - **What it is**: A directory containing logs of all changes made to references (branches, HEAD).
        - **Purpose**: Stores information about updates to the repository, such as branch changes and commits, allowing you to see a history of reference updates
    - **packed-refs**:
        - **What it is**: A file that stores references in a compact form.
        - **Purpose**: Over time, as references grow, Git might pack them into a single file for efficiency. This reduces the number of loose files in the refs/ directory.
    - **branches/** (optional):
        - **What it is**: A legacy directory that used to contain references to branches
        - **Purpose**: It’s largely obsolete now, as branches are handled via the refs/heads/ directory.
- What are **Git hooks** ?
    - **Git hooks** are scripts that Git automatically executes before or after specific events in the Git lifecycle.
        - These scripts allow you to automate tasks, enforce policies, or trigger actions during different stages of Git operations, such as committing, merging, pushing, or receiving updates from a remote repository.
    
    ---
    
    **Types of Git Hooks**
    
    1. **Client-Side Hooks**:
        
        These run on the developer’s local machine during operations such as committing, merging, and pushing.

        - **pre-commit**: Runs before the commit process starts. You can use this hook to check for code formatting, run tests, or lint your code before allowing a commit.
        - **commit-msg**: Runs after the user has entered a commit message. It can be used to validate the commit message format.
        - **pre-push**: Runs before a push to a remote repository. It can be used to run tests or check for specific conditions before allowing a push.
    2. **Server-Side Hooks**
        
        These run on the Git server during operations such as receiving pushes from clients.
        
        **Common Server-Side Hooks**:
        
        - **pre-receive**: Runs before a push is accepted on the server. It can be used to enforce policies such as rejecting commits that don’t meet certain criteria.
        - **post-receive**: Runs after the push has been accepted. This hook is often used to trigger deployment scripts or notify systems that new code has been pushed.
- How are **Git Hooks Implemented**?

        - Each hook is a separate file, and the name of the file corresponds to the hook it implements *(e.g., pre-commit, post-commit, etc.)*
        - By default, when you initialize a Git repository, you’ll find sample hook scripts in the `.git/hooks/` directory, usually ending with `.sample`
        - These are example hooks that you can rename and modify to suit your needs.
    
    ---
    
    **Steps to Implement a Git Hook**:
    
    1. **Navigate to the hooks directory:**
        

    2. **Create or modify a hook script**:
        - Rename an existing sample file (e.g., `mv pre-commit.sample pre-commit`) or create a new script file (e.g., `touch pre-commit`).
        - Ensure the script is executable:
            
            ```bash
            chmod +x pre-commit
            ```
            
    3. **Test the hook** by performing the action it is associated with (e.g., making a commit for pre-commit).

- What are merge conflicts in Git, and how should they be handled?
    - **Merge conflicts** in Git occur when Git is unable to automatically reconcile differences between two branches during a merge operation.
        - This typically happens when changes are made to the same lines of code in the same file on both branches, or when a file is modified in one branch and deleted in another.
        - When Git encounters such a scenario, it cannot automatically determine which changes should be kept, and it will prompt you to manually resolve the conflict.
    
    ---
    
    **How to Handle Merge Conflicts**
    
    1. **Identify the Conflict**
        
        When a merge conflict occurs, Git will stop the merge process and indicate which files have conflicts. You can see which files are in conflict by running:
        
        ```bash
        git status
        ```
        
        > Conflicted files will be listed as “both modified.”
        > 
    2. **Open the Conflicted Files**
        
        Open the files with conflicts in a text editor or an Integrated Development Environment (IDE). Git marks the conflicting sections in the file with the following markers:
        
        ```bash
        <<<<<<< HEAD
        Changes from the current branch (e.g., main)
        =======
        Changes from the branch being merged in (e.g., feature-branch)
        >>>>>>>
        ```
        
        - The section between <<<<<<< HEAD and ======= contains the changes from the current branch (e.g., main).
        - The section between ======= and >>>>>>> contains the changes from the branch being merged (e.g., feature-branch).
    3. **Resolve the Conflict**
        - Decide which changes to keep:
            - **Keep changes from the current branch**: Delete the lines from the branch being merged.
            - **Keep changes from the branch being merged**: Delete the lines from the current branch.
            - **Combine changes**: Edit the lines to combine both changes in a way that makes sense.
        - After resolving the conflict, remove the conflict markers (<<<<<<<, =======, >>>>>>>).
    4. **Stage the Resolved Files**
        
        Once you’ve resolved the conflicts, stage the resolved files:
        
        ```bash
        git add <filename>
        ```
        
    5. **Complete the Merge**
        
        After staging the resolved files, complete the merge with:
        
        ```bash
        git commit
        ```
        
        Git will use a default merge commit message, but you can edit it if necessary.
        
- What are the **Best Practices to Avoid Merge Conflicts ?**
    1. **Commit Frequently and Pull Regularly:**
        - Regularly pulling changes from the main branch (or the branch you’re merging into) and committing your changes frequently can help reduce the likelihood of conflicts.
            - This keeps your branch in sync with the latest changes and helps catch conflicts early.
    2. **Work on Small, Isolated Features**:
        - Instead of making large, sweeping changes in a single branch, break down your work into smaller, manageable chunks.
            - This reduces the overlap with other developers’ changes and makes conflicts easier to resolve if they occur.
    3. **Communicate with Your Team**:
        - Communication is key in a collaborative environment.
            - Make sure your team knows what parts of the codebase you are working on, especially if you’re modifying critical or shared files.
    4. **Rebase Before Merging**:
        - Rebasing your branch onto the latest version of the target branch before merging can help avoid conflicts by integrating the latest changes before the final merge.
            - This results in a cleaner, linear history but should be done with care, especially on shared branches.
        
        ```bash
        git checkout feature-branch
        git fetch origin
        git rebase origin/main
        ```
        
    5. **Use Feature Branches**:
        - Isolate your work in feature branches, and only merge into the main branch when the feature is complete.
            - This makes it easier to handle conflicts because you’re merging well-defined changes.
    6. **Review and Test Before Merging**:
        - Code review and automated testing can catch potential conflicts and issues before they reach the main branch.
            - Always review and test changes before merging.
- **What is the `--no-ff` Option in `git merge branch --no-ff`?**
    - The `--no-ff` option in Git is used during a merge operation to ensure that the merge creates a new commit even if a *fast-forward merge* is possible.
        - **By default**, if the branch you are merging can be “fast-forwarded,” Git will simply move the branch pointer forward to the latest commit, and no new merge commit will be created.
        - The --no-ff option forces Git to create a merge commit, preserving the history of the branch being merged.
    
    ---
    
    **Fast-Forward Merge (Default Behavior)**
    
    - A **fast-forward merge** occurs when the branch you are merging can be “fast-forwarded” because there are no divergent commits on the target branch. In other words, the branch being merged is directly ahead of the current branch, and Git can simply move the branch pointer forward without creating a new merge commit.
        - This results in a linear history with no additional merge commit.
    
    ```bash
    A---B (main)
         \
          D---E (feature)
    ```
    
    ```bash
    A---B---D---E (main)
    ```
    
    - **Pros**: Simple, linear history.
    - **Cons**: No explicit record of the branch structure or the fact that a feature branch was merged.
    
    ---
    
    **No Fast-Forward Merge (--no-ff)**
    
    - **How it Works**: The `--no-ff` option creates a merge commit even if the branch could be fast-forwarded.
        - This merge commit records the exact point at which the branches were merged, preserving the history and structure of the branch.
    
    ```bash
    A---B (main)
         \
          C---D (feature)
    ```
    
    ```bash
    A----B------E (main)
          \    /
           C---D (feature)
    ```
    
    > * **`E`** is the merge commit
    > 
    - **Pros**: Preserves the history of the branch structure, clearly showing where branches were merged.
    - **Cons**: Results in a more complex history with additional merge commits, which can be unnecessary for trivial changes.
    
    ---
    
    **Key Differences between Fast Forward and Rebase**
    
    - **Operation**
        - **Fast-Forward:** When you perform a fast-forward merge, Git simply moves the main branch pointer to the latest commit on the feature branch, assuming main has not diverged from feature.
        - **Rebase:** Rebasing moves the entire set of commits from feature and applies them on top of the main branch as if they were made on main from the start. This rewrites the commit history
    - **Commit History:**
        - **Fast-Forward Merge**: Does not change commit hashes or rewrite history; it simply moves the branch pointer forward.
        - **Rebase**: Rewrites history by creating new commits on top of the target branch.
    - **Branch Merging**:
        - **Fast-Forward Merge**: The branch history is lost, as it appears as though the feature commits were always part of the main line.
        - **Rebase**: The commits are re-applied, creating a new linear sequence on top of the main branch.
    - **Use Cases**:
        - **Fast-Forward Merge**: Useful when you want a simple, linear history and don’t need to preserve the context of a separate branch.
        - **Rebase**: Useful for keeping the history clean and avoiding unnecessary merge commits, especially when integrating feature branches into the main branch.
